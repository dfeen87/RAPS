# RAPS 4.0.0 — BEDROCK Engineering Baseline

## Why a major release

RAPS 4.0.0 establishes a BEDROCK baseline after a bottom-up review of the policy,
stability-monitor, HIL transport, test, and CI boundaries. The architecture was
preserved where sound; the guarantees underneath it were strengthened. RAPS uses
the major increment here as an engineering milestone. It also contains intentional
behavioral-contract tightening: malformed safety inputs that could previously pass
without a violation are now rejected.

## Explicit invariants and changed failure behavior

- Scalar, slew-rate, and duration policies fail closed for malformed measurements,
  malformed limits, and invalid time intervals. NaN comparisons and a zero or
  negative interval can no longer silently authorize a value.
- Stability samples must contain finite, non-negative stress magnitudes and a
  strictly increasing timestamp. Invalid samples latch the monitor unsafe and are
  reported as `INVALID_INPUT`; they do not replace the last valid rate-history
  sample.
- A HIL operation may lazily connect, but connection establishment must not attempt
  to acquire the device mutex recursively. The transport now uses one locked helper
  for both explicit and lazy connection paths.

These are fail-closed changes. Callers that relied on non-finite policy inputs,
non-positive slew intervals, negative durations or out-of-order stability updates
being accepted must treat the new violation result explicitly.

## Regression evidence and CI enforcement

- Policy regressions cover NaN, infinity, inverted bounds, non-positive time, and
  negative duration.
- Stability regressions cover malformed and stale samples, the unsafe latch, and
  clean recovery without poisoned derivative history.
- A loopback HIL rig regression proves that the first operation auto-connects and
  completes; a five-second test timeout permanently guards against deadlock.
- CI runs the complete SIL suite in Debug and Release, keeps C/C++ assertions active
  for test targets, and compiles the REST API integration surface in both profiles.

## Architecture and compatibility

The existing PDT → policy/DSM → governed execution → telemetry architecture, HAL
interfaces, public data types, and observability-only REST API remain in place. No
new service, global mutable state, persistence format, or dependency was introduced.
The changes are source-compatible, but intentionally stricter at malformed-input
and event-ordering boundaries.

## Remaining validation requirements

The repository tests demonstrate software behavior only. They do not certify flight
worthiness, physical models, real-time deadlines, hardware drivers, network fault
tolerance, or regulatory compliance. Representative HIL campaigns, hardware and
environmental qualification, requirements traceability, hazard analysis, independent
verification, and the applicable aviation certification process remain required
before operational use. The external publications and physical claims referenced by
the project were not revalidated as part of this repository-only pass.
